# 为什么改用原生定时检查

决定日期：2026-09-12。当前主分支采用“原生定时触发 → 单轮读取 → 新结果验收”，退役工具内持续轮询，保留会话池、派发轮次、答复基线和独立验收。

## 原方案遇到的问题

旧公开版本默认每 15 秒读取会话、每段等待 15 分钟，主控通过 `wait` 收取结果并按需续段。后续私人静默原型希望仅在完成时返回，让本地同时做其他工作；它未作为新版本发布，现已退役。

实际使用中仍出现反复列出、读取，以及主控续接和进度消息。程序读取不等于模型每次都完整分析网页，但收取、续接和生成进度会让主控再次参与，不能把“脚本静默”说成“主控零参与、零额度”。

期间出现过 `Too many requests`。高频读取是值得降低的请求来源，但没有服务端归因或受控对照，不能断言脚本是原因，也不能保证 7 分钟检查消除限流。

## 为什么选新方式

| 关注点 | 工具内持续轮询 | 原生定时检查 |
| --- | --- | --- |
| 运行组织 | 维护在途调用、返回编号和续段 | 宿主管理安排，每次一轮检查 |
| 请求频率 | 短间隔重复读取相同状态 | 明确周期，每轮最多一次列表刷新和一次目标读取 |
| 本地统筹 | 收取、续接容易反复占用主控 | 本轮结束后不需维持等待调用，可做独立工作 |
| 维护 | 自制脚本、测试、返回结构和恢复逻辑 | 移除轮询脚本，保留检查规则与租约 |
| 发现速度 | 正常情况下较快 | 接受一个周期左右的发现延迟，另受调度、网络和限流影响 |

7 分钟是本次需求的折中，不是测得的最佳周期或平台保证的最大延迟。新方案仍是低频轮询，不是网页事件直接推送；改变的是调度方式，不是让模型永久在线。

## 为什么不保留旧方式

旧方式并非原理上不可行，过去通过的测试也不因此失效。但它未满足本次最看重的“减少主控续接和无变化读取、简化维护”的体验要求。两套机制同时保留容易导致重复检查和恢复混淆，因此不再提供旧脚本作为备用入口。

也不采用“网页写完成文件 → 云盘同步 → 本地监听”：这会额外依赖网页规范输出、同步及时性和本地监听；文件到达本身仍不能让已结束的主控任务自动恢复，文件存在也不证明产物合格。文件通道只承担交付，不承担唤醒协议。

如果以后宿主提供可核验的普通网页会话完成事件订阅，可以另行评估；当前不假装已有这项能力。

## 边界

- 定时触发仍可能消耗模型额度；尚无可比的新旧 token 总量，不能承诺节省比例。
- 不发无变化通知只是减少打扰，不是后台没有请求。
- 本轮新实质答复且空闲才是候选，本地仍核对内容、版本和测试证据。
- 不改变账户权限、额度或安全规则，不承诺跨休眠或退出持续运行。

部署与迁移见 [等待与恢复](等待与恢复.md)。历史验证仅适用于当时范围，不证明新方案在所有宿主可用。
