# 定时检查、恢复与卸载

当前方案使用用户授权的 Codex 原生定时检查，不再加载 JavaScript 静默等待程序。调度由宿主管理，会话池继续记录账号、租约与事件。选择理由见 [为何改用定时检查](为何改用定时检查.md)。

## 建立检查

1. 核对宿主实际具备普通 ChatGPT 会话的列出、读取、发送接口，以及原生定时自动化工具。缺少定时能力时报告缺口，可由用户手动要求检查，不自行恢复旧脚本或创建系统服务。
2. 派发成功后保留 `job_id`、`thread_id`、真实派发轮次 `dispatchTurnId` 和发送前答复基线 `baselineMessageId`。发送不确定或新轮次尚不可读时先核对，不绑定旧轮次、不重发。
3. 用户授权后，优先使用附着当前本地统筹任务的原生检查（宿主若称为 heartbeat，以实际工具定义为准）。先查并复用已有匹配安排，不重复创建。普通网页会话不能套用仅支持本地 Codex 任务的完成通知接口。
4. 定时任务保存准确标识、输入版本、周期与处理规则。当前项目选择每 7 分钟一次，这是可调整的取舍，不是所有任务的强制默认值；宿主不支持时报告，不悄悄替换。

通过实际自动化工具创建、更新、暂停或删除安排，不手写宿主配置。本仓库不含私人任务 ID 或可直接导入的个人定时配置；部署文档不会自动启用检查。

## 每次触发

每次只做一轮：最多刷新一次会话列表、读取一次目标会话，不在本轮循环、睡眠或连续续接 `wait`。

| 观察结果 | 本轮处理 |
| --- | --- |
| 仍在运行或只有旧答复 | 结束本轮，保留任务，等下次；不发送无变化进度。 |
| 本次派发后有新实质答复且会话空闲 | 暂停对应检查，记录候选，再验收实际结果。 |
| `Too many requests` / 限流 | 本轮不重试、不换账号规避；若服务指定更长重试时间，遵守它。 |
| 身份不匹配、权限拒绝、状态不明或需要用户处理 | 不当作空闲或成功；报告实际缺口，必要时暂停。 |

候选正文被截断时，先暂停周期检查，再按宿主分页能力完整回收后验收。定时触发可能消耗模型额度；“无变化保持安静”不等于零请求或零 token。

## 续接与并行

同角色返工继续原任务、会话与租约，只发送新增内容一次，核对新的轮次与答复基线，再更新并恢复原检查。多个已授权且无冲突的任务分别维护标识和检查安排，不因一个完成就回收其他任务。

验收通过、任务取消或不再需要跟进后停用对应检查。暂停检查不取消网页执行，也不证明目标机器命令已停止。恢复先核对原租约、原会话、已有命令会话、输入版本和已完成产物，再继续未完成步骤，不重复副作用。明确安全拒绝不通过改写任务、换账号或通道绕过。

## 从旧版升级

核对旧等待调用是否在途，在实际宿主中结束属于本任务的旧调用；此动作不取消网页任务。更新仓库及已安装的“网页执行”参考入口，移除加载旧脚本的指令。原发布的 `网页会话池/等待网页结果.js` 与配套测试已从当前版本移除，不另存可运行备用副本，不改写历史 Git 提交。

保留账号、数据库、租约、环境与文件交付配置。用户同意周期后再启用定时检查，不能同时运行两套机制。

## 卸载

先处理在途角色并停用本方案的检查，再按安装记录移除本方案拥有且未被另改的全局块和技能文件。不停用其他项目的安排。数据库、任务记录及用户文件默认保留，不用旧整文件备份覆盖后来的用户配置。
